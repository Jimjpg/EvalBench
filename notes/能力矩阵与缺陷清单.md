**矩阵解读**：四大基准沿"问题覆盖 × 规模"军备竞赛（36 题 / 6,482 实例 / 11,000 变量 → 10M 城市级），但第 ⑤⑥ 列（成本记录与预算控制）和第 ⑧ 列（失败模式编码）系统性薄弱——CO-Bench 与 FrontierCO 完全不记 token，HeuriGym 与 DynaSchedBench 记录了 token 却都无预算上限，成本在四家中至多是事后统计量，无一带预算档位实验。EvalBench 刻意反向取舍，是表中唯一把预算作为每次运行事前硬约束（三重控制器 + BudgetExhausted 正常收尾计 F5）、绘制成本-质量前沿图（QYI vs ¥）、全量 transcript 落盘（YAML 快照 + git 哈希 + prompt_version 的完整审计链）、失败模式 F1–F6 自动编码并与预算信号交叉统计的迷你体系（原计划的三档预算实验已按降级预案①裁剪，预算-性能曲线列为后续工作）。指标层直接收编两家精华（FrontierCO 的 primal gap 双分支公式 + HeuriGym 的 QYI 调和平均），并补上全矩阵无人作为一等指标报告的稳定性（stability_cv）。规模上以三个数量级以上的差距小于 CO-Bench / FrontierCO（3 问题 3 规模 45 实例 vs 6,482 实例 / 10M 节点），用"成本受控 + 可复现"的深度换问题广度——四大基准回答"LLM 能力边界在哪"，EvalBench 回答"给定预算与锁定协议，能力-成本曲线长什么样、失败以什么模式发生"。

## 二、领域评测缺陷清单

**D1 指标口径不统一：各基准分数不可比，标准化是被明确呼吁的 open problem**
- 问题描述：同一批模型在不同基准上的"分数"没有共同语义——CO-Bench 用 min/max 比值、HeuriGym 用截断比 + 调和平均、FrontierCO 用有界 primal gap、领域惯用 gap=100×(Z_llm−Z_best)/Z_best（可超 100%），跨基准结果无法换算，也无法判定"改进"是真进步还是口径差异。
- 文献证据：Ros 综述（103 篇 PRISMA 综述）附录 D 表 5 罗列 Hypervolume、IGD、F1、PAR10、Compile/Runtime Error Rate、Throughput 等大量异构指标，§7 原文明言 "developing standardized evaluation protocols and identifying suitable metrics" 是 promising research direction；CO-Bench 笔记指出其 min/max 比值在 h 与 h* 符号相反时失真（h=−5, h*=3 → s=0.6，明显高估）；FrontierCO 脚注指出路由文献常用 gap 定义（可超 100%）与其有界 primal gap 不可直接换算。
- EvalBench 对策：W2 指标体系文档（Task 2.1）规定每指标 = 名称 / 精确公式 / 取值范围 / summary.csv 采集列 / 文献出处五要素；metrics.py 以 TDD（12 个测试）锁死 primal gap（FrontierCO 式双分支）、quality（HeuriGym 式）、QYI、stability_cv 四个口径；参考解统一由 OR-Tools 生成并注明 30 s 时间限口径，杜绝"同一指标不同真值"的隐性口径漂移。

**D2 成本维度缺失或浅表：token 有零星记录，但无一家设预算上限、无一家做预算档位实验**
- 问题描述：成本在整个领域要么不记录，要么只做事后统计——没有任何基准把"预算"作为事前控制变量，更没有系统考察"预算档位 → 性能"曲线。
- 文献证据：Ros 综述通篇无 per-study cost 字段（仅个别研究自发报告 Runtime / API Call Rate），§6.1.5 指出传统 CO 评测惯例应含 computational times 与统计检验但 LLM 研究普遍未继承；CO-Bench"正文与附录均无 token 消耗 / API 费用统计"；FrontierCO 无 token / API 量化（附录 G 仅定性），LLM 每实例 64×300 s + 3600 s 的复合成本未折算货币；HeuriGym 记录了 token（Gemini-2.5-Pro 单轮 2.88M prompt + 0.46M completion）并把 API 价格表入正文、画 0–10 美元成本-质量散点图，但"未对'最多花多少钱'设熔断机制——成本是事后统计量而非控制变量"；DynaSchedBench 把 token 升为一等指标（L1+Tool 12.614M vs L1 CoT 4.016M，三倍成本未见收益）但同样"没有硬预算上限 / 截断机制"。
- EvalBench 对策：三重预算控制器 Budget(max_calls, max_tokens, max_seconds)（超限抛 BudgetExhausted 并正常收尾、计为 F5）把成本变成每次运行的事前硬约束；api_cost 按带核对日期的价格表折算，项目级熔断线 ¥50；成本-质量前沿图（QYI vs ¥）对应可检验假设 H4（两模型 QYI 接近但 QYI/¥ 性价比差异显著）。原计划的三档预算实验（tight/standard/loose × 3 规模）与假设 H3（预算收紧对大规模实例伤害最大）已按降级预案①裁剪（2026-10-06，课程时间约束），预算-性能曲线列为后续工作——但与四基准"成本最多是事后统计量"相比，预算作为事前控制变量这一核心主张不变。

**D3 可复现协议不完整：提示词不透明、模型版本不锁定、chat 输出非确定性三重叠加**
- 问题描述：从"用了什么模型"到"用什么提示词"再到"能否复现同一次输出"，链条每一环在现有文献中都有断点，使报告的进步无法归因也无法复现。
- 文献证据：Ros 综述乱象清单第 2/3/4/5 条——103 篇动用 70 个 LLM / 22 种架构、命名混乱且综述期间多款已弃用（Text-Davinci-003 → GPT-4o 等）；7 篇实验研究完全不写用了什么 LLM；"Documenting the exact prompts used is crucial" 但普遍缺失；chat completions 默认非确定性（"no guarantee of consistent responses"）；49% 为未经评审的预印本；闭源付费模型限制复现。CO-Bench 未声明 prompt 全量公开与 API snapshot / 种子锁定；FrontierCO 的 FunSearch / ReEvo 底座模型版本未披露；FuzzGPT（迁移证据）主力模型 Codex (code-davinci-002) 闭源且已被 OpenAI 弃用、主结果无法严格复现——跨领域实证了"不锁定版本"如何摧毁可复现性。反例证明可做到：HeuriGym 把模型锁定到 API 快照（gemini-2.5-pro-preview-05-06）并全文公开提示词。
- EvalBench 对策：W2 评测协议文档（Task 2.2）五节——YAML 配置快照原样落盘 run 目录；模型名 + temperature 写入 config；git commit 哈希写入 manifest.json；提示词固化在 problems/*.py 的 prompt() 方法中随仓库版本化、manifest 另记 prompt_version；每次 LLM 调用完整回复落盘 transcripts/；并以"诚实性声明"直面 API 非逐 token 确定性——以"配置 + 日志全留存"实现审计式可复现，报告 Discussion 节讨论此局限。

**D4 失败模式只有定性描述：无系统分类、无跨模型统计、无失败-预算关联**
- 问题描述：约束遗漏、幻觉、搜索停滞等失败在各基准中以散文式归纳出现，缺统一分类编码、缺跨模型占比统计，更没有"失败如何随预算 / 规模变化"的分析，导致改进无从对症。
- 文献证据：CO-Bench 定性归纳 5 条（如 "struggle to ensure the feasibility of solutions"），量化只到 Valid Solution 粗粒度（一次性生成约 30%、最好 agent 0.5555 < 人类 0.6111），规划弱于随机采样（AIDE 0.7534 < BestOfN 0.7743）也无失败类型分解；FrontierCO 报告 LLM "high variance due to their incapability in understanding effectiveness of different algorithms"（hard CVRP 6.52% vs TSP 35.82%、std ±48.67%）、OOM（CPMP-hard FunSearch 77.32%）、词云显示只会复现 SA / LNS——但无分类编码；DynaSchedBench 给出机理级发现（可观测性悖论 L3 1.66% vs L2 0.65%；Reflection 1.7% 差于 CoT 0.7% 且 token 14.47M vs 6.88M）但为个案条目而非可复用分类法；做得最完整的 HeuriGym 也只有四分类 + 六类异常日志（幻觉 API 触发 ModuleNotFoundError、全局布线 9 模型 SOLVE^III 全 0），未与成本或预算关联。FuzzGPT（迁移证据）证明失败样本可系统再利用：历史 bug 触发程序做种子使覆盖率比 TitanFuzz 高 36.03% / 60.70%，CoT"先写失败成因再生成"进一步提升覆盖（23,945 vs 22,922），且低预算下高效（FS-25 以 25 程序/API 超 TitanFuzz 全量）——失败驱动闭环在测试领域已验证，LLM×OR 评测中尚无人做。
- EvalBench 对策：W2 失败模式分类文档（Task 2.3）定义 F1 解析失败 / F2 约束违背 / F3 幻觉 / F4 搜索停滞 / F5 预算耗尽 / F6 其他六类，配自动判定规则（parse() 返回 None、violations 含"越界 / 不存在"、相邻两轮 cost 相等、BudgetExhausted 捕获）、优先级 F5>F1>F3>F4>F2>F6、主类别唯一；runner 自动标注、人工仅复核 F6 与抽检 10%（W4 Task 4.4）；F5 与预算档位天然交叉，使"失败分布 × 预算 × 规模"成为可统计的三维表；transcripts 全量落盘，为 FuzzGPT 式"失败种子驱动的困难实例生成"（设计层扩展）保留原料。

**D5 稳定性几乎无人报告：方差被定性提及，重复实验设计缺位**
- 问题描述：LLM 采样非确定性使单次运行分数带随机噪声，但四基准均未把"同配置重复 k 次"作为受控实验设计，方差至多以跨实例标准差的面目出现。
- 文献证据：FrontierCO 明确观察到 LLM "high variance"与"数值不稳定"（FunSearch TSP-hard ±25.62%、MDS-easy ±48.67%），但结果均为单次运行、标准差来自多实例而非重复，且 Self-Refine 仅用单一模型 o4-mini；CO-Bench 与 HeuriGym 均为单次运行（HeuriGym 温度固定 0、o 系列仅支持 T=1，无重复报告）；最接近的是 DynaSchedBench 的每配置 5 个独立种子——但那是控制实例生成侧随机性（消除"随机雾"），模型侧跨运行重复仍未做；Ros 综述指出 chat 默认非确定性，却未统计任何研究的重复次数。
- EvalBench 对策：stability_cv = pstdev/mean（对同实例 k 次重复的 primal_gap 序列）作为一等指标进 metrics.py 与 summary.csv；稳定性实验 exp_stability.yaml（2 模型 × 3 问题 × 3 规模 × 3 实例 × 5 重复 = 90 runs，temperature 0.7）产出跨重复分布而非仅均值；报告以"均值 ± CV"呈现，使"模型 A 均值略高但方差大"类结论可检验。

**D6 基准规模与真实性矛盾：一端是 10–100 条目的 toy 自产自销，另一端是 10M 节点的区分度坍塌**
- 问题描述：领域在"过小"与"过大"两极同时失效——小基准碎片化且常被提出者自用，无法反映真实应用规模；极端大规模基准上多数方法直接 OOM / 超时，gap=1 的记录只测出"能否产可行解"，解质量梯度反而消失。
- 文献证据：Ros 综述乱象第 1 条——多数专用数据集仅 10–100 量级条目（Almonacid 10、Michailidis 18、ComplexOR 37、OptiChat 63、NLP4LP 67、IndustryOR 100），"The remaining datasets have been used exclusively in one out of the retrieved studies"（其余数据集只被 1 篇使用、且往往就是提出者本人），且综述"未系统报告各研究所用实例的规模"；FrontierCO 三大局限指出现有 ML4CO 基准惯用比真实应用小若干数量级的 toy 实例（TSP-10K / MIS-11K）、此前进展被高估（LEHD 在合成基准 0.72% gap → easy TSP 10% → hard TSP 77%）；但同文局限自认 10M 级实例使多数神经方法 OOM / 超时，"hard 集上大量 gap=1 的记录更多反映'能否产出可行解'而非解质量梯度，区分度在极端规模上反而下降（MDS-hard 神经方法全部 100%）"。
- EvalBench 对策：显式取中间路线——3 问题 × 3 档规模（TSP n=10/50/200 等）× 5 实例，全部选可确定性机器验证的问题（可行性由组合性质精确判定，不依赖大规模参考求解器）；跨规模泛化作为可检验假设 H1（可行率随规模增大显著下降，HeuriGym / FrontierCO 的已知现象）；规模 × 预算交叉（原 H3）已随降级预案①裁剪，列为后续工作；报告 Discussion 中说明这是"以深度换广度"的课程级取舍，大规模扩展列为后续工作。

## 三、与方向的对照

对照主文档方向五（"成本受控、可复现的 LLM 与 OR 评测体系"）列出的 10 个评价维度：EvalBench 覆盖其中 8 个并各配落地机制——解质量对应 quality_score（HeuriGym 式 clip(ref/cost, 0, 1)），可行率对应 evaluate() 验证器输出的（模型, 问题, 规模）分组可行率并与质量合成 QYI，最优性差距对应 primal_gap（FrontierCO 式，相对 OR-Tools 参考解且注明 30 s 口径），运行时间对应预算控制器与客户端计量的 seconds，LLM 调用次数对应 Budget.calls 计数，token / API 成本对应 tokens_in / tokens_out / api_cost 三列（价格表带核对日期）、¥50 熔断线与每次运行的三重预算硬约束（三档预算实验已按降级预案①裁剪，列为后续工作），跨规模泛化对应 3 档规模 × 5 实例与假设 H1，稳定性对应 stability_cv 与 5 次重复实验。有意裁剪两个维度：内存算力以运行时间近似替代（课程环境为单机 CPU、无 GPU / 内存计量，与 FrontierCO 附录 G 只能定性讨论算力成本同理）；解释忠实性列为展望（但 transcripts/ 全量落盘保留了解释性分析的全部原始材料，未来可对"自述推理与实际行为的一致性"做事后审计）。取舍理由是课程项目规模约束——单人六周、API 预算估算 < ¥30（熔断线 ¥50），必须把 10 维裁剪为可机器计量、可小样本检验的 8 维，并把被裁剪维度的数据接口保留在协议层而非彻底丢弃；这本身就是对缺陷清单 D2（成本必须成为受控变量）与 D6（规模取舍应显式声明）主张的实践。
