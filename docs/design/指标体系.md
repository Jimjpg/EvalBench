## 1. 动机：为什么不只比目标函数值

如果只报告"目标函数值"，第一个崩塌的是跨结果可比性。W1 缺陷清单 D1 表明，同一批模型在不同基准上的"分数"没有共同语义：CO-Bench 的 min/max 比值在 h 与 h\* 符号相反时失真（h=−5, h\*=3 得 s=0.6，明显高估）；路由文献惯用的 gap=100×(Z−Z\*)/Z\* 可超 100%；FrontierCO 的有界 primal gap 又与前两者不可换算。Ros 综述（103 篇 PRISMA 综述）附录 D 表 5 罗列 Hypervolume、IGD、F1、PAR10、Compile/Runtime Error Rate 等大量异构指标，并在 §7 明言 "developing standardized evaluation protocols and identifying suitable metrics" 是被明确呼吁的 open problem。因此本文对每个指标执行五要素定义——名称、精确公式、取值范围、summary.csv 采集列、文献出处——并以 TDD（metrics.py 配 12 个测试）把口径锁死在代码里，杜绝"同一个名字、两种含义"的隐性漂移。

第二个崩塌的是失败归因。单一分数无法区分"没产出解""产出但不可行""可行但极差"三种完全不同的失败：HeuriGym 全局布线 9 个模型 SOLVE^III 全 0，若只看分数，"0 分"掩盖了失败发生在哪个里程碑。EvalBench 继承其三阶段漏斗思想——feasible 先行（能否产出可行解）、quality / primal_gap 后判（可行解有多好）、failure_class 兜底（不可行时失败属于哪一类），三层信息各行其是、同表采集。

第三个崩塌的是成本盲区。四大基准中 CO-Bench 与 FrontierCO 完全不记 token，HeuriGym 与 DynaSchedBench 记录了 token 却都无预算上限、更无预算档位实验——成本在整个领域至多是事后统计量（D2）。本项目的立意即"成本受控"：tokens_in / tokens_out / calls / seconds 与质量指标同表采集，api_cost 按带核对日期的价格表折算，配合 Budget 三重熔断（超限抛 BudgetExhausted 并计为 F5），成本-质量前沿图（report.py 图 1）是与主指标并列的一等产出。

第四个崩塌的是置信度。LLM 采样非确定性使单次运行的分数带随机噪声（D5）：FrontierCO 观察到 LLM 高方差（FunSearch TSP-hard std ±25.62%、MDS-easy ±48.67%）但其结果为单次运行、标准差来自跨实例而非重复；CO-Bench 与 HeuriGym 均为单次运行（HeuriGym 温度固定 0）；最接近的 DynaSchedBench 每配置 5 个种子，控制的也只是实例生成侧随机性，模型侧跨运行重复仍未有人做。EvalBench 把 stability_cv 升为一等指标写进 metrics.py 与图表（report.py 图 4），并以 5 次重复实验（exp_stability.yaml，temperature 0.7）供数——"模型 A 均值略高但方差大"从此是可检验的陈述而非印象。

最后，指标须服务于改进而不只是排名。failure_class（F1–F6）随每行采集，使失败分布可与模型 × 规模交叉统计（report.py 图 5），其中 F5（预算耗尽）天然携带预算信号；原计划的"失败 × 预算档位"三维交叉已随降级预案①裁剪（2026-10-06），列为后续工作，为"对症改进"提供入口（D4）。综上，八个指标构成五个维度的证据链——质量（primal_gap、quality）、可行性（feasible、QYI）、成本（tokens_in、tokens_out、calls、seconds、api_cost）、稳定性（stability_cv）、失败（failure_class）。这是对 D1"标准化呼吁"的具体回应，也同时补上 D2 / D4 / D5 的系统性缺口。

## 2. 指标总表

**采集载体**：`results/<run_id>/summary.csv`，每行 = 一次 `solve_once`，即"模型 × 实例 × 重复"的一轮完整智能体循环（生成 → 解析 → 验证 → 反馈，至多 max_iters 轮）。行键 = (model, problem, scale, instance, repeat)；实例由种子确定性生成（`problem.generate(n, seed)`，实例名形如 `tsp_n10_s1`）。列序固定 18 列（runner.py `fields` 原文，行 1451–1454）：

```python
fields = ["run_id", "model", "problem", "scale", "instance", "repeat",
          "status", "feasible", "cost", "reference", "primal_gap",
          "quality", "failure_class", "tokens_in", "tokens_out",
          "calls", "tokens", "seconds"]
```

**八个指标**（公式与《计划》代码逐字对齐；QYI / api_cost / stability_cv 为分析层派生指标，不直接落列，表中"采集列"一栏如实标注其数据来源列与计算位置）：

| 指标名 | 精确公式 | 取值范围 | summary.csv 采集列 | 文献出处 |
|---|---|---|---|---|
| **primal_gap** | `primal_gap(cost, ref)`：<br>① cost 为 None 或非有限 → `1.0`<br>② `denom = max(abs(cost), abs(ref))`；`denom == 0` → `0.0`（双方皆零）<br>③ `cost × ref < 0`（符号相反）→ `1.0`<br>④ 否则 `abs(cost − ref) / denom` | [0, 1]；不可行 = 1，正常取值下可行解 < 1 | `primal_gap` | FrontierCO 式 2；渊源 Berthold 2006 / 2013、Achterberg et al. 2012、11th DIMACS Implementation Challenge |
| **feasible**（可行率） | 行级：`int(max_iters 内取得可行解)`，取 0/1<br>组级：按 (model, problem, scale) 分组对行级 feasible 求均值 | 行级 {0, 1}；组级 [0, 1] | `feasible` | HeuriGym YIELD = N̂/N（可行解产出率）同构 |
| **quality** | `quality_score(cost, ref)`：<br>① cost 为 None 或 cost ≤ 0 → `0.0`<br>② 否则 `max(0.0, min(1.0, ref / cost))` | [0, 1] | `quality` | HeuriGym QUALITY = (1/N̂)Σ min(1, c\*_n/c_n)（截断比） |
| **QYI** | `qyi(q, y)`：q = 组内 quality 均值，y = 组内可行率<br>① `q + y = 0` → `0.0`<br>② 否则 `2·q·y / (q + y)` | [0, 1] | 无直接列；由 `quality`、`feasible` 两列在分析层计算（report.py 图 1） | HeuriGym QYI = (1+β²)·Q·Y/(β²·Q+Y)，β=1 调和平均（类比 F-score） |
| **tokens_in / tokens_out / calls / seconds** | `tokens_in = Σ 各轮 prompt_tokens`，`tokens_out = Σ 各轮 completion_tokens`（client 计量，transcript 求和）<br>`calls = Budget.calls`（成功调用计数）<br>`seconds = Budget.elapsed`（实例级墙钟，`round(·, 2)`） | tokens_in / out ≥ 0（整数）；calls ≥ 0（整数）；seconds ≥ 0 | `tokens_in`、`tokens_out`、`calls`、`seconds`（另有 `tokens` 列，恒等于 tokens_in + tokens_out） | HeuriGym Table 24 token 全量记录；DynaSchedBench token 一等指标；预算控制为本作业 D2 对策 |
| **api_cost** | `Σ_rows [tokens_in/1e6 × p_in + tokens_out/1e6 × p_out]`<br>`PRICE = {"deepseek-chat": (2.0, 8.0), "qwen-plus": (0.8, 2.0)}`（元 / 1M tokens，输入 / 输出；**运行当日到官网核对并更新注释日期**） | [0, +∞) 元 | 无直接列；由 `tokens_in`、`tokens_out` 两列 × PRICE 折算（report.py `cost_yuan`；表 1 列名 `yuan`） | HeuriGym Table 6 API 价格表 + 成本-质量散点图（其图 2 右图） |
| **stability_cv** | `stability_cv(values)`：values = 同 (model, problem, instance) 的 k 次重复 primal_gap 序列<br>① 滤除 None / 非有限值<br>② `len(vals) < 2` → `0.0`（单值）<br>③ `m = mean(vals)`；`m == 0` → `0.0`<br>④ 否则 `pstdev(vals) / m` | [0, +∞)；完美稳定 = 0 | 无直接列；由 `primal_gap` 列按 (model, problem, instance) 分组计算（report.py 图 4） | DynaSchedBench 每配置 5 种子（最近似先例）+ FrontierCO 高方差观察（±25.62% / ±48.67%）；本作业 D5 对策 |
| **failure_class** | `label_failure(status, transcript)`：F1 解析失败 / F2 约束违背 / F3 幻觉 / F4 搜索停滞 / F5 预算耗尽 / F6 其他<br>优先级 F5 > F1 > F3 > F4 > F2 > F6，主类别唯一<br>status 以 "solved" 开头 → `""`（无失败） | {F1…F6, ""} | `failure_class` | HeuriGym 四分类 + 六类异常自动归类（其 Fig 3）；判定规则详见 `docs/design/失败模式分类.md` |

**表注**：

1. **派生指标的位置是刻意设计**：QYI / api_cost / stability_cv 不落 summary.csv 列——summary.csv 只记"不变的事实"（原始 token 数、每行 gap / quality / feasible / 失败编码），派生量留在分析层（report.py 只读 summary.csv）。价格修订或聚合口径调整后，对历史 run 重算即可，无需重跑实验。
2. **tokens 与 tokens_in + tokens_out 恒等**：`Budget.record_call(prompt_tokens + completion_tokens)` 与 transcript 求和来自同一次 chat 返回的 usage，故 `tokens` 列恒等于 `tokens_in + tokens_out`。两套口径并存是因为预算熔断（budget.py）与成本折算（report.py）是两个模块各取所需。
3. **seconds 的口径**：从 Budget 构造（solve_once 开头）计到 row 组装（`snapshot()`），覆盖整轮"生成 → 解析 → 验证 → 反馈"循环的墙钟，含本地解析 / 验证时间；不等于 API 延迟之和——逐轮 API 延迟在 transcripts 的 `latency` 字段（见评测协议文档 §4）。
4. **quality 的 cost ≤ 0 分支**：三个问题的目标值均为正（TSP 巡回长度、BPP 箱数、P\|\|Cmax makespan），cost ≤ 0 意味着输出荒谬，quality 直接记 0——防御性口径，与 HeuriGym 截断比语义一致。

## 3. 指标设计决策论证

### 3.1 为什么 primal_gap 与 quality 双指标并存：有界严格性 vs 直观可解释性

只看一个比值指标必然在某个场景失真。primal_gap 提供严格性：严格有界 [0, 1]（0 = 恰好达到参考，1 = 最差），不可行解一律记 1、正常取值下可行解 gap < 1，满足"不可行解永不优于可行解"的评测公理；符号分支（cost·ref < 0 → 1）直接防住 CO-Bench min/max 比值的符号失真（h=−5, h\*=3 → 0.6 的教训）；且不设截断。但它以"到参考的距离"度量、左右对称——比参考好 10% 与差约 10% 的 gap 读数相近，且 0.0909 这类数字（test_gap_basic：primal_gap(110, 100) = 10/110）需要换算才能向非专业读者解释。quality 提供直观性：1 = 达到或超过参考，0.8 = 花了参考 1.25 倍的成本（test_quality_worse：quality_score(125, 100) = 0.8），语义自解释，且与 HeuriGym QUALITY（min(1, c\*/c)）同口径、跨文献可比；代价是截断——达到参考即满分，领先幅度被抹平。两者由同一 (cost, reference) 对计算、零额外采集成本，却在"参考解可能非严格最优"的现实下（§5：medium / large 档参考为启发式）互补成对：LLM 解优于参考时 quality 记 1、gap 记小正值，两个读数合起来刻画"达到并略超参考"的状态；单用任一指标都会丢失一半信息。TDD 以 5 个 gap 测试（test_gap_\*）+ 3 个 quality 测试（test_quality_\*）把两个口径锁死。

### 3.2 为什么 QYI 用调和平均而非算术平均：强惩罚失衡

HeuriGym 把 QYI 定义为 quality 与 yield 的 β=1 调和平均并明言类比 F-score，理由是"比算术平均更强惩罚失衡"。算术平均的失效模式很具体：q=1.0、y=0.1 时算术平均 0.55（看似过半），调和平均 2×1×0.1/1.1 ≈ 0.18（暴露"解得好但十次里九次不可行"）；q=0.3、y=0.3 时两种平均同为 0.3（不奖励单维冒尖）。评测要回答的问题恰恰是"模型是均衡还是偏科"，调和平均使任何一块短板直接压低总分，防止"不可行率高但偶尔惊艳"的模型靠质量均值得分。边界 q+y=0（全不可行且 quality 全 0）定义为 0，避免除零（test_qyi_zero_when_both_zero）。同时逐组分报 q 与 y（表 1 的 quality / feasible 均值列），保留"能解题但解得差"vs"解得好但常不可行"权衡结构的可见性——这也是 HeuriGym 的同款做法。

### 3.3 为什么 api_cost 需要价格表 + 核对日期：定价是易变口径

模型定价与模型版本一样是易变口径：HeuriGym 局限 7 自认"模型迭代快、快照版本会过时"；Ros 综述记录 103 篇动用 70 个 LLM、综述期间多款已弃用——今天折算的成本数字，三个月后用新价表重算就会变。因此 PRICE 表配两条纪律：其一，单价硬编码于 report.py 并带注释"运行当日到官网核对并更新注释日期"（代码注释原文），使核对成为可追责的实验步骤而非口头承诺；其二，价格只存在于分析层——summary.csv 记录的是不变的原始 token 数，货币成本永远是派生量（`cost_yuan`），价格修订后对历史 run 重算即可、无需重跑。这是 D3"版本锁定"精神在货币维度的延伸，做法直接取自 HeuriGym Table 6（API 价格表入正文，$/百万 token）与其成本-质量散点图；项目级另有 ¥50 熔断线（见实验设计文档）。

### 3.4 为什么 stability_cv 用变异系数而非标准差：跨实例可比

不同 (模型, 问题, 规模) 组的 primal_gap 均值水平差异天然很大——大规模实例普遍高 gap、小规模普遍低 gap。同样 σ=0.05，在 μ=0.1 的组是 50% 的相对波动，在 μ=0.8 的组只有 6%：直接比较标准差会系统性高估高均值组的稳定性、低估低均值组的不稳定。变异系数 pstdev/mean 无量纲、跨组可比——FrontierCO 报告的 ±25.62% / ±48.67% 正是相对波动口径的先例（但其数值来自跨实例而非同实例重复，这正是 D5 批评的缺口）。边界口径与代码一致：单值序列（k=1，重复未启用）→ 0，不制造噪声；均值 0（全 0 gap，完美稳定）→ 0；序列先滤除 None / 非有限值（防御式分支）。两个 TDD 测试（test_stability_cv_matches_definition、test_stability_single_value_is_zero）锁死定义。

## 4. 聚合层级：实例级 → 分组级 → 模型级

### 4.1 实例级（summary.csv 每行）

一行 = 一次 solve_once = (model, problem, scale, instance, repeat) 的完整智能体循环。行内直接可得 12 个结果列（status、feasible、cost、reference、primal_gap、quality、failure_class、tokens_in、tokens_out、calls、tokens、seconds，外加 6 个键列，共 18 列，全文见 §2 前言）。实例由 seed 确定性生成，行键可复现。

### 4.2 分组级：(model, problem, scale)

report.py 表 1 的聚合单元（行 1628–1633）：

```python
tbl = (df.groupby(["model", "problem", "scale"])
         .agg(gap=("primal_gap", "mean"),
              feasible=("feasible", "mean"),
              yuan=("cost_yuan", "sum"),
              tokens=("tokens", "sum"))
         .round(4).reset_index())
```

落盘为 `table1_summary.csv`。图 2 / 图 3 再按 (model, scale) 对 primal_gap / feasible 求均值并按 `["small", "medium", "large"]` 排序。§2 指标 2 的组级可行率与 QYI 的 q、y 均在此层定义。

### 4.3 模型级：加权 QYI

report.py 图 1（行 1556–1560）：对每个模型取 q = 全体行 quality 均值、y = 全体行 feasible 均值、`QYI = 2·q·y/(q+y)`（q+y=0 → 0）、cost = cost_yuan 总和，产出成本-质量前沿散点。当各分组行数相同（主实验设计：每组合 5 实例 × 1 重复），全体行均值 = 各分组均值的等权平均，等价于 HeuriGym 按任务实例数加权的加权 QYI；行数不均衡时该均值自动退化为按实例数加权，语义仍是"平均到每一次求解"。

### 4.4 聚合规则

- **质量 / 率类**（primal_gap、quality、feasible）：**算术平均**——对 gap 取算术平均与 FrontierCO 的汇总方式一致；
- **资源类**（tokens、api_cost、seconds）：**总和**——token、时间、货币是加性资源，总和直接对应预算熔断口径（Budget 的 max_tokens / max_seconds 与项目 ¥50 熔断线均以总量计）；
- 与 FrontierCO 的一处刻意差异：其对求解时间取几何平均（关心求解器效率的中位水平），EvalBench 对时间取总和（关心预算消耗）——因为时间是本项目的事前约束变量（D2），不是事后效率统计；
- 代码对应：mean 已实现于表 1 的 gap / feasible 与图 1 的 q / y；sum 已实现于表 1 的 yuan / tokens；seconds 依同一资源规则求和（用于报告的成本-时间核算）。

## 5. 参考解口径

### 5.1 统一原则

所有 primal_gap / quality 的 `reference` 一律由本地确定性求解器计算（`evalbench/baselines/baselines.py`），绝不取自 LLM 输出或外部数据库；结果按 `f"{problem.name}/{inst.name}"` 缓存于 `results/references.json`（references.py——"30s GLS 只算一次，控制本地算力成本"）。经典贪心基线（TSP = 最近邻 + 2-opt、BPP = FFD、调度 = LPT，Task 2.4 Step 4 基线对照表）同时充当参考解的回退路径，一物两用。

### 5.2 分支规则（baselines.py 逐字口径，时间限统一 30 s）

| 问题 | 精确分支 | 参考解性质 |
|---|---|---|
| TSP | n ≤ 10：全排列暴力枚举（itertools.permutations），`round(best, 3)`；n > 10：OR-Tools 路由求解器，`FirstSolutionStrategy.PATH_CHEAPEST_ARC` + `LocalSearchMetaheuristic.GUIDED_LOCAL_SEARCH` + `time_limit.FromSeconds(30)`，坐标距离 ×1000 取整为整数弧成本，`ObjectiveValue()/1000.0` 还原；OR-Tools 无解 → 回退 NN + 2-opt | small 档（n=10）真最优；medium（n=50）/ large（n=200）为 30 s 限时搜索 |
| BPP | 物品数 > 25：FFD 启发式箱数；≤ 25：CP-SAT 精确（FFD 提供箱数上界 ub；AddExactlyOne + 容量约束；`Minimize(sum(used))`；`max_time_in_seconds=30`；OPTIMAL / FEASIBLE 取 `ObjectiveValue()`，否则回退 ub） | small 档（20 项）30 s 内最优或可行；medium（60）/ large（120）为 FFD 上界 |
| P\|\|Cmax | 作业数 > 25：LPT makespan；≤ 25：CP-SAT 精确（时长 ×10 取整入模型；`Minimize(ms)`；30 s；`ObjectiveValue()/10.0`；否则回退 LPT） | small 档（20 作业）精确；medium（60）/ large（120）为 LPT 上界 |

三问题的 small 档全部落在精确分支、medium / large 全部落在启发式分支——规模档与求解口径恰好对齐（sizes 表：TSP 行 562、BPP 行 715、P\|\|Cmax 行 790–791）。

### 5.3 非严格最优的诚实声明

1. **medium / large 档的参考解不是严格最优**：FFD / LPT 是启发式上界、GLS 是限时搜索，真最优可能更好。因此本文所有 gap / quality 一律读作"相对 OR-Tools 30 s 口径参考解"，不读作"相对真最优"。这与 FrontierCO 的 BKS 标准化思路同源（其 BKS 缺失时也用 SOTA 求解器限时跑），也与 HeuriGym 局限 5 的自认一致（"专家基线取文献最好已知启发式而非真最优，QYI=1 的语义依赖基线质量"）。
2. **参考解偏松（劣于真最优）时的读数**：LLM 更容易拿到 quality=1（截断口径偏乐观）；若 LLM 找到优于参考的解，gap = (ref−cost)/ref > 0 而 quality = 1——双指标合读正确刻画"达到并超过参考"，但"超过多少"被 quality 截断、被 gap 对称化，需回看 `cost` 与 `reference` 原始列（summary.csv 均有）。
3. **TSP 的 NN + 2-opt 回退**：若触发，代码注释明确要求"口径需在报告注明"——回退实例清单在报告中如实列出。
4. **口径变更必须显式**：references.json 的缓存 key 不含时间限参数——若调整 `time_limit_s`，须删除 `results/references.json` 重算，否则新旧口径会静默混用；本协议规定任何参考解口径变更都必须显式清缓存并在报告声明。
