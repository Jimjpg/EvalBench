## 1. 配置快照：实验 = 目录 + 配置

**机制**（`Runner.__init__`，runner.py 行 1405–1414）：

1. `yaml.safe_load` 读入 `configs/<exp>.yaml`；
2. 生成 run_id：`datetime.now().strftime("%Y%m%d-%H%M%S") + "-" + uuid.uuid4().hex[:6]`——秒级时间戳保证可读，6 位随机后缀保证同秒不冲突；
3. 创建 `results/<run_id>/transcripts/`；
4. 将读入的配置原样写出：`yaml.safe_dump(self.cfg, f, allow_unicode=True)` → `results/<run_id>/config.yaml`。

**为什么"跑过的实验 = 目录 + 配置"即可审计**：

- 实验的全部自由度收敛于一个 YAML——模型名、端点、密钥环境变量名、温度、问题、规模档、每档实例数、重复数、迭代上限、三重预算（max_calls / max_tokens / max_seconds）——配置文件即实验的完整参数化描述，无隐式状态；
- run 目录自包含：config.yaml（参数）+ manifest.json（版本锚，§2）+ summary.csv（结构化结果）+ transcripts/（原始对话，§4），四件套离开任何外部环境仍可完整回答"当时跑了什么、跑出了什么"；
- 断点续跑强化"目录 = 实验"的等式（`run()`，行 1455–1472）：启动时从既有 summary.csv 重建 `done = {(model, problem, scale, instance, repeat), …}`，同配置重启自动跳过已完成行——中断恢复不需要任何额外记账，拿同一 config 再跑一次即可；
- 对照 D3：Ros 综述记录"7 篇实验研究完全不写用了什么 LLM"，根因是配置与结果分离存放、配置靠事后回忆；EvalBench 把配置物理写进结果目录，"忘记录配置"在机制上不可能发生。

## 2. 版本锁定：模型、代码、提示词三层锚定

D3 的证据链是三重叠加的断点：模型版本不锁定（Ros 综述：103 篇动用 70 个 LLM、命名混乱且多款已弃用；FrontierCO 的 FunSearch / ReEvo 底座模型未披露；FuzzGPT 主力模型 code-davinci-002 已被弃用致主结果无法严格复现）+ 提示词不透明（Ros："Documenting the exact prompts used is crucial" 但普遍缺失）+ 输出非确定性（§5）。对策分三层：

**（a）模型与采样参数 → config**：`models[].name`（deepseek-chat / qwen-plus）、`models[].temperature`（默认 0.7）、`base_url`、`env_key` 全部写入 YAML，随 config.yaml 快照落盘；runner 构造客户端时逐字段读取：

```python
llm_factory = lambda m: LLMClient(
    model=m["name"], base_url=m["base_url"],
    api_key=os.environ.get(m["env_key"]),
    temperature=m.get("temperature", 0.7))      # 行 1445–1448
```

**（b）代码与提示词 → git commit 哈希**：`_manifest()` 以 `subprocess.run(["git", "rev-parse", "--short", "HEAD"])` 取短哈希写入 manifest.json（异常时记 `"unknown"`，行 1416–1422）。关键设计：**提示词不放在配置或数据库里，而是固化在 `problems/*.py` 的 `prompt()` 方法中**——题面、输入格式说明、输出 JSON schema 全是代码；验证器（evaluate）、解析器（parse）、迭代反馈模板（runner.py 内"你上一轮的尝试未通过验证，错误信息：…"，行 1364–1366）同样是代码。因此一个 git 哈希同时锁定提示词、验证器与反馈话术：**提示词即代码，代码即版本**。manifest 另记两个字段使提示词不读代码也可见：`prompt_version`（当前 `"v1"`）与 `system_prompt` 全文（`"你是一名运筹优化专家，必须严格按用户要求的 JSON 格式输出。"`，行 1330–1331、1426–1429）。

**（c）依赖 → requirements.txt**：openai>=1.40、ortools>=9.8、pyyaml>=6.0 等（Task 3.1 Step 2）随仓库版本化。

**与领域最佳实践的对照与差距**：HeuriGym 是可复现性的标杆——模型锁定到 API 快照（gemini-2.5-pro-preview-05-06、claude-3-7-sonnet-20250219）、第三方库钉死（numpy==2.2.5）、提示词全文公开（附录 B）。EvalBench 的现实约束：DeepSeek / Qwen 商用端点不提供带日期的快照版本号，`deepseek-chat` 这一模型名背后的权重可能随服务端升级而变，无法逐字复刻 HeuriGym 级锁定。务实形态：模型名 + `created` 时间戳 + 全量 transcript（§4）——transcript 记录了当日实际输入输出，任何权重漂移都可被事后审计发现。此差距在第 5 节诚实声明中一并讨论。

## 3. 运行目录结构

《计划》第 1 节（行 85–90）的 run 目录树原文：

```
├── results/                       # 运行输出（git 忽略，报告引用）
│   └── <run_id>/
│       ├── config.yaml            # 配置快照
│       ├── manifest.json          # run_id / 时间 / git 哈希 / 提示词版本
│       ├── summary.csv            # 每实例一行汇总
│       └── transcripts/           # 每实例完整对话与解析记录
```

逐项说明：

| 条目 | 产生者 | 内容与用途 |
|---|---|---|
| `results/<run_id>/` | `Runner.__init__` | run_id = `%Y%m%d-%H%M%S-<uuid6>`；一个目录 = 一次实验 |
| `config.yaml` | `Runner.__init__`（yaml.safe_dump 原样落盘） | 实验全部参数（§1）；审计入口 |
| `manifest.json` | `Runner._manifest()` | 5 字段：`run_id`、`created`（ISO 8601 秒）、`git_commit`（短哈希或 "unknown"）、`prompt_version`（"v1"）、`system_prompt`（全文）——版本锚（§2） |
| `summary.csv` | `Runner.run()` 逐行追加 | 18 列（清单见指标体系文档 §2 前言），每实例每重复一行；断点续跑的依据；report.py 的唯一输入 |
| `transcripts/{problem}_{instance}_r{repeat}.json` | `Runner.run()` 每实例写一个 | `{"row": …, "transcript": […]}`，原始对话全量（§4） |

**分析阶段追加产物**（report.py `make_all(run_dir)`，只读 summary.csv、不改动以上原始四件套）：`figs/fig1_cost_quality.png`、`fig2_gap_vs_scale.png`、`fig3_feasible_vs_scale.png`、`fig4_stability.png`、`fig5_failure_modes.png` 与 `table1_summary.csv`。另有参考解缓存 `results/references.json`（references.py，key = `{problem.name}/{inst.name}`）位于 results/ 根、跨 run 共享。

**仓库与 run 目录的分工**：`.gitignore` 忽略 `results/` 与 `.env`（原始数据体积大、API 密钥敏感），因此审计链分两半——**仓库（代码 + configs/ + requirements.txt）锁定"怎么跑"，run 目录锁定"跑出了什么"**，二者以 manifest.json 的 `git_commit` 字段焊接：从 run 目录反查仓库版本，从仓库版本正推提示词与验证器语义。冒烟通过后打 git tag（v0.1-smoke）作为可复现锚点（Task 3.9 Step 5）。

## 4. 原始数据留存：transcripts 全量落盘

**文件与结构**：每实例每重复一个 JSON——`transcripts/{problem.name}_{inst.name}_r{rep}.json`，内容为 `{"row": row, "transcript": transcript}`（json.dump，ensure_ascii=False，indent=2，行 1481–1486）。`row` 与 summary.csv 该行完全同构（18 字段）；`transcript` 是轮次数组，每轮 9 个字段（solve_once，行 1374–1381）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `iter` | int | 轮次，1..max_iters |
| `raw` | str | LLM 完整回复原文（未经任何截断 / 清洗） |
| `parsed` | bool | `parse()` 是否成功提取规定 JSON |
| `prompt_tokens` / `completion_tokens` | int | 该轮输入 / 输出 token（来自 API usage，client.py 行 1185–1186） |
| `latency` | float | 该轮 API 延迟秒数（round 2 位） |
| `feasible` | bool | 该轮解是否通过验证器 |
| `cost` | float 或 null | 该轮目标值；不可行为 null |
| `violations` | list[str] | 验证器违规描述；解析失败时为 `["解析失败"]` |

**为什么必须落 raw 原文**：API 非确定性（§5）意味着"模型当时说了什么"事后无法重取——raw 是唯一的第一证据；同时它是失败模式人工复核（失败模式分类文档：F6 全量复核 + 自动标注 10% 抽检）与解析失败（F1）归因的原料。FuzzGPT 的方法论启示（D4 扩展接口）也依赖全量 transcript：历史失败样本可系统再利用为困难实例生成种子。

**row 与 transcript 的派生关系可编程验证**：`tokens_in = Σ prompt_tokens`、`tokens_out = Σ completion_tokens`、feasible / cost / status / failure_class 由轮次结果派生——审计时可写脚本核对两层数据自洽。

**实现注记（如实记录）**：文件名模板不含模型名，而外层循环 `for m in self.cfg["models"]`（行 1461）在最外，故多模型 run 中同一 (problem, instance, repeat) 的 transcript 文件会被后一个模型覆盖。W3 实现 Task 3.7 时应在文件名中加入模型前缀或按模型分子目录，方能兑现"每次 LLM 调用完整回复落盘"的准绳；本文以准绳为准，文件名模板为实现细节。此为对《计划》代码的如实观察，非新增机制。

## 5. 诚实性声明：审计式可复现，而非位级复现

**不可消除的局限**：Ros 综述明确指出 chat completions 默认非确定性（"no guarantee of consistent responses"），且其统计中没有任何研究报告重复次数；商用 API 即使固定 temperature 也不承诺逐 token 复现。因此 EvalBench 不宣称位级复现（重跑得到逐字节相同输出）。

**实际承诺——审计式可复现**：四层留存构成完整审计链——① config.yaml（参数全集）② manifest.json（git 哈希 + prompt_version + system_prompt 全文）③ transcripts/（每次调用的完整输入输出）④ summary.csv（结构化结果）。任何人可以：在同一 git 哈希下重建输入（配置 + 提示词 + 由种子确定性生成的实例）、核对输出（transcript 原文）、重算指标（report.py 只读 summary.csv）。每个数字可追溯到一次具体的 API 调用；但重跑不保证相同数字。

**随机性不是被回避的缺陷，而是被测量的对象**：temperature=0.7 下的输出波动由稳定性实验（exp_stability.yaml，2 模型 × 3 问题 × 3 规模 × 3 实例 × 5 重复 = 90 runs）直接量化，报告为"均值 ± stability_cv"（衔接指标体系文档 §2 指标 7 与 §4 聚合）。对照 HeuriGym 温度固定 0 也只做单次运行、无重复方差报告——EvalBench 在此点上超出范本。

**这是加分区**：报告 Discussion 一节将专门讨论该局限。直面局限比回避局限更有学术价值——Ros 综述列举的乱象（模型版本不写、提示词不公开、非确定性不讨论）多数源于"不报告"而非"不存在"；把不可消除的随机性升为一等指标（stability_cv）、把不可完整锁定的版本做成可审计链条（§2 的 git 哈希 + transcript），这本身就是对 D3 / D5 的方法论回应，也是本作业区别于"只报喜"文献的立场声明。

## 6. YAML schema 注释版

`configs/exp_smoke.yaml` 全文（《计划》Task 3.1 Step 4 原文，行 296–313）：

```yaml
run_name: smoke
models:
  - name: deepseek-chat
    base_url: https://api.deepseek.com
    env_key: LLM_API_KEY
    temperature: 0.7
problems:
  - name: tsp
    scales: [small]
instances_per_scale: 1
repeats: 1
max_iters: 2
budget:
  max_calls: 3
  max_tokens: 20000
  max_seconds: 120
```

逐字段注释（"读取处"均指 runner.py，行号见第 7 节核对表）：

| 字段 | 冒烟值 | 语义 | runner.py 读取处 |
|---|---|---|---|
| `run_name` | smoke | 实验语义标识 | **无程序化读取点**：作为配置标识随 config.yaml 快照落盘，供人工辨识实验用途（《计划》Task 3.1 Step 4 原文字段） |
| `models[].name` | deepseek-chat | API model 名 | `LLMClient(model=m["name"])`（行 1446）；写入 summary.csv 的 `model` 列（`row["model"] = llm.model`，行 1390）；匹配 report.py PRICE 表单价（行 1541） |
| `models[].base_url` | https://api.deepseek.com | OpenAI 兼容端点 | `LLMClient(base_url=m["base_url"])`（行 1446）；Qwen 走 DashScope 兼容端点（密钥 `DASHSCOPE_API_KEY`，Task 3.9 Step 1） |
| `models[].env_key` | LLM_API_KEY | API 密钥的环境变量名 | `api_key=os.environ.get(m["env_key"])`（行 1447）；密钥本体放 `.env`（python-dotenv `load_dotenv()`，行 1495），.gitignore 忽略——密钥名入库、密钥值不入库 |
| `models[].temperature` | 0.7 | 采样温度 | `m.get("temperature", 0.7)`（行 1448，缺省 0.7）→ LLMClient → 每轮 chat 请求的 temperature 参数（client.py 行 1180） |
| `problems[].name` | tsp | 问题注册名 | `PROBLEMS[p["name"]]()`（行 1464，registry.py 注册表） |
| `problems[].scales` | [small] | 规模档列表 | `for scale in p["scales"]: n = problem.sizes[scale]`（行 1465–1466）；TSP sizes = {"small": 10, "medium": 50, "large": 200} |
| `instances_per_scale` | 1 | 每档实例数 | `for seed in range(1, cfg["instances_per_scale"] + 1): inst = problem.generate(n, seed)`（行 1467–1468）——实例由 seed 确定性生成，配置 + 代码即可复现实例本身 |
| `repeats` | 1 | 同实例重复次数 | `cfg.get("repeats", 1)`（行 1470，缺省 1）；`for rep in range(1, repeats + 1)`——稳定性实验设 5 |
| `max_iters` | 2 | 智能体循环上限 | `cfg.get("max_iters", 5)`（行 1477，缺省 5）→ solve_once 的 `for it in range(1, max_iters + 1)`（行 1361） |
| `budget.max_calls` | 3 | 调用次数熔断 | `Budget(**(budget_cfg or {}))`（行 1358）→ Budget.max_calls；check() 中 `calls >= max_calls` 抛 BudgetExhausted → status="budget_exhausted" → failure_class="F5"（budget.py 行 1140–1141；runner.py 行 1387、1339） |
| `budget.max_tokens` | 20000 | token 总量熔断 | 同上 → Budget.max_tokens；`tokens >= max_tokens` 熔断（budget.py 行 1142–1143） |
| `budget.max_seconds` | 120 | 墙钟时间熔断 | 同上 → Budget.max_seconds；`elapsed >= max_seconds` 熔断（budget.py 行 1144–1145）；`Budget.snapshot()` 产出 `calls` / `tokens` / `seconds` 三列（行 1147–1149） |

**对应关系总述**：六个顶层键中，`models` / `problems` / `instances_per_scale` / `repeats` / `max_iters` / `budget` 均在 `Runner.run()`（行 1461–1477）有读取点；`run_name` 为纯标识字段（见注）。`exp_main` / `exp_stability` 共用同一 schema，仅改值。原计划的 `exp_budget_{tight,standard,loose}`（tight calls=3、seconds=120；standard calls=10、seconds=600；loose calls=20、seconds=1800）已按降级预案①裁剪（2026-10-06）——预算控制器与 standard 档预算值（calls=10, tokens=60000, seconds=600）仍用于主/稳定性实验的每次运行。
