## 1. 动机：从散文式归纳到可统计编码

W1 缺陷清单 D4 指出：失败模式在现有基准中以散文式归纳出现，缺统一分类编码、缺跨模型占比统计、更没有"失败如何随预算 / 规模变化"的分析，导致改进无从对症。证据链横跨四家：CO-Bench 定性归纳约 5 条（如 "struggle to ensure the feasibility of solutions"），量化只到 Valid Solution 粗粒度——一次性生成约 30% 正确、最好 agent 0.5555 仍低于人类专家 0.6111、规划能力弱于随机采样（AIDE 0.7534 < BestOfN 0.7743）——无失败类型分解；FrontierCO 报告高方差（hard CVRP 6.52% vs TSP 35.82%、std ±48.67%）、OOM（CPMP-hard FunSearch 77.32%）、词云分析（只会复现 SA / LNS），但均为观察条目而非编码；DynaSchedBench 给出机理级发现（可观测性悖论 L3 1.66% vs L2 0.65%；Reflection 1.7% 差于 CoT 0.7% 且 token 14.47M vs 6.88M），却是个案条目而非可复用分类法。没有分类编码，"哪个模型败在哪、败得多频繁"就永远是印象而非统计。

领域内做得最完整的是 HeuriGym：四分类失败（幻觉 API / API 误用 / 算法逻辑错误 / 约束误解）+ 六类异常自动归类（Import / Runtime / Syntax / Timeout / Verification / API Error），Fig 3 按模型统计失败占比。但它的分类对象是**程序执行过程**——其被测智能体输出的是完整启发式程序（典型 300+ 行），失败以异常类型面目出现（ModuleNotFoundError、SyntaxError、VerificationError）。EvalBench 的智能体循环（生成 → 解析 → 验证 → 反馈迭代）输出的是**解的 JSON 表示**而非程序，失败发生在**解的生成过程**：能否从回复中提取解对象（F1）→ 解对象是否引用真实存在的实体（F3）→ 是否满足组合与容量约束（F2）→ 迭代是否还在产生新候选（F4）→ 运行环境是否还有预算（F5）。两套分类维度不同、互不可替代：HeuriGym 的 SyntaxError 在我们的循环中没有对应物（没有程序可抛语法错），我们的 F5 在其体系中也无对应物（它无预算闸门）。F1–F6 不是对四分类的简化或复制，而是另一维度上的完整编码；语义上的两个交点是"约束误解 ↔ F2"与"幻觉 API ↔ F3"——后者尤其说明"幻觉"现象跨维度稳定存在，只是幻觉的对象从库 API 换成了解空间实体（城市 / 物品 / 机器下标）。

EvalBench 分类法的三条设计目标由此确定。其一，**每类失败锚定一个确定性代码信号**（parse() 返回值、violations 字符串、cost 序列、BudgetExhausted 异常），判定全自动、机器可复判——对照 D4 批评的"散文式归纳"，编码必须先于解释存在。其二，**主类别唯一**（§2.1），使失败分布成为可加总的统计量（图 5、§5 交叉表）。其三，**F5 携带预算信号**，使失败分布天然可与环境约束交叉——这是对 D2"成本必须成为受控变量"在失败维度的延伸。需如实注明：原设计使 F5 与三档预算（tight / standard / loose）交叉构成"失败 × 预算 × 规模"三维表，该交叉已随降级预案①（2026-10-06）裁剪，预算维度坍缩为 standard 单档，三维交叉列为后续工作（§5.3）；但 F5 本身不受影响——每次运行仍受三重硬约束，预算耗尽事件仍发生、仍被编码。

## 2. 分类法：六类失败的定义与判定

### 2.1 总则：判定对象、终态原则与分支结构

**判定对象**是每个失败的 run（一次 `solve_once`，即"模型 × 实例 × 重复"的完整智能体循环）。status 以 `solved` 开头的 run 无失败类（`failure_class = ""`）；其余 run 恰归一类，**主类别唯一**——由 `label_failure(status, transcript)` 的单返回值保证，写入 summary.csv 的 `failure_class` 列（runner.py 行 1398）。

**终态原则**：除 F5（环境信号）外，判定一律基于 transcript 的**末轮**状态（末轮 `parsed`、末轮 `violations`、末两轮 `cost`），而非全程任意轮次。理由：失败类要回答"这次运行**最终**败在哪"；迭代过程中的中间失败已被反馈—修正循环消费（test_solve_once_parse_then_fix：第 1 轮解析失败、第 2 轮修正成功 → solved，无失败类），不应重复计入。F1 只在"到最后一轮仍无法解析"时成立。

**分支结构**（label_failure 权威实现，runner.py 行 1336–1355，按代码顺序）：

| 序 | 代码分支（行号） | 条件 | 返回 |
|---|---|---|---|
| 0 | 1338–1339 | status 以 "solved" 开头 | `""`（无失败） |
| 1 | 1340–1341 | status == "budget_exhausted" | **F5** |
| 2 | 1342–1343 | transcript 为空 | F6（防御分支，见 §2.10） |
| 3 | 1344–1345 | 末轮 `parsed` == False | **F1** |
| 4 | 1346–1348 | 末轮 violations 含"越界"或"不存在" | **F3** |
| 5 | 1349–1352 | 末两轮 cost 相等且非 None | **F4** |
| 6 | 1353–1354 | 末轮 violations 非空 | **F2** |
| 7 | 1355 | 以上皆否 | **F6** |

声明优先级 **F5 > F1 > F3 > F4 > F2 > F6**（函数 docstring 原文，行 1337）；设计理由见 §2.9。分支 2 的空 transcript 守卫在代码顺序上先于 F1，这不是优先级声明的一部分，而是必要防御——后续分支访问 `transcript[-1]`，空列表会抛 IndexError。

### 2.2 F1 解析失败（parse failure）

- **定义**：无法从模型输出中提取规定 JSON 格式的解对象。
- **判定规则（自动）**：末轮 `parse()` 返回 None，即 `transcript[-1]["parsed"] == False`（行 1344–1345）。parse 失败轮的 violations 为占位值 `["解析失败"]`（solve_once 行 1372–1373），evaluate() 未被调用。
- **判定依据（代码信号）**：三个问题的 `parse()` 均为"正则提取首个 `{...}` → json.loads → 校验规定键（tour / bins / assign）为 list"三步（tsp.py 行 607–616 等），任一步失败返回 None；TDD 锚点 test_tsp_parse_garbage_returns_none、test_label_failure_f1（行 1267–1269）。
- **预期频率**：**中**。先验：HeuriGym 最好模型 SOLVE^I@1=100%（前沿模型格式遵从近乎完美），但 deepseek-chat / qwen-plus 为中端模型；本项目 prompt 已含格式示例与"只输出 JSON"指令、解析器已容错 markdown 围栏（test_tsp_parse_from_markdown_fence），《计划》风险表仍将"LLM 输出解析成功率过低"列为中等概率风险；且 TSP large 档需输出 200 元素排列，长输出截断 / 格式漂移风险随规模上升。预测：小规模低、大规模升高。
- **对应文献现象**：HeuriGym 六类异常中的 SyntaxError / API Error（输出格式不合规）；Ros 综述"指令遵循"缺陷；DynaSchedBench 四大持续局限之一即指令遵循弱。

### 2.3 F2 约束违背（constraint violation）

- **定义**：解析成功、解对象结构合法，但不满足问题的组合完整性或容量约束——数量不足 / 缺失 / 重复 / 超容量。
- **判定规则（自动）**：末轮 violations 非空、且不含"越界 / 不存在"字样、且不满足 F4 条件（行 1353–1354）。F2 是 F3 排除后的**默认不可行类**。
- **判定依据（代码信号）**：三问题验证器的完整性 / 容量违规文本——TSP："路线城市数不等于 n"（行 577）、"路线含非整数元素"（行 580）、"城市缺失或重复访问"（行 586）；BPP："解不是箱的列表"（行 731）、"物品缺失或重复装箱"（行 740 / 742）、"物品集合不正确"（行 743 兜底）、"存在箱子超过容量"（行 747）；调度："指派长度不等于作业数"（行 807）、"指派含非整数元素"（行 810）。TDD 锚点 test_bpp_evaluate_missing_item、test_label_failure_f2_plain_infeasible（行 1278–1280）。
- **预期频率**：**高**（预期为占比最大的类）。先验：可行性是领域主瓶颈——HeuriGym 最好模型 SOLVE^III@10 仅 74.8%（即最优者也有约四分之一失败）、全局布线 9 模型全 0；CO-Bench 自述模型 "struggle to ensure the feasibility of solutions"、一次性生成约 30% 全对；FrontierCO 不可行解一律 pg=1。且大规模下输出 n 元素排列的完整性维护（不重不漏）难度陡增，F2 预计随规模上升。
- **对应文献现象**：HeuriGym 四分类之"约束误解"（VerificationError）——本分类法与其最直接的语义对应点；CO-Bench"可行性约束处理不足"。

### 2.4 F3 幻觉（hallucination）

- **定义**：解对象引用了不存在于该实例的实体——下标越界（城市下标 ≥ n、物品下标 ≥ n、机器编号 ≥ m）。
- **判定规则（自动）**：末轮 violations 含"越界"或"不存在"（行 1347–1348）。
- **判定依据（代码信号）**：三问题验证器的越界文本——TSP"城市下标越界"（行 583，先于缺失 / 重复检查）、BPP"物品下标越界"（行 738）、调度"机器编号越界"（行 813）；TDD 锚点 test_tsp_evaluate_rejected_on_out_of_range、test_label_failure_f3_on_out_of_range（行 1272–1275）。**如实注明**：当前三问题的违规文本只产出"越界"，不含"不存在"字样——"不存在"是分类法预留的关键词（对应 Task 2.3 定义"引用不存在的对象（下标越界、物品不存在）"），覆盖未来问题或 prompt v2 反馈模板可能出现的"对象不存在"表述；当前幻觉信号统一落在"越界"上。
- **预期频率**：**中**，且随规模上升。先验：HeuriGym 四分类之"幻觉 API"（调用不存在的库接口触发 ModuleNotFoundError）证明该现象真实且跨模型分布（Fig 3）；解空间越大（n=200 的 TSP、m=12 的机器编号），长序列生成中的计数漂移与越界概率越高；DynaSchedBench 的指令遵循弱佐证。
- **对应文献现象**：HeuriGym"幻觉 API"——同一认知缺陷（对可用对象集合的错误信念）在不同任务维度（库 API vs 解空间实体）上的稳定复现。

### 2.5 F4 搜索停滞（search stagnation）

- **定义**：迭代中连续两轮 cost 完全相同且不可行——反馈循环已不再驱动模型产生新候选（《计划》Task 2.3 原文口径）。
- **判定规则（自动）**：`len(costs) >= 2 and costs[-1] is not None and costs[-1] == costs[-2]`（行 1349–1352），在 F1 / F3 排除之后判定。
- **判定依据（代码信号）**：transcript 各轮 `cost` 字段的末两位相等且非空。**可达性注记（如实记录，详见 §2.10）**：三问题验证器对不可行解一律返回 `cost=None`，而任何 feasible=True 的轮次会立即 break 并记 solved——因此在当前问题族上，失败 run 的 transcript 中所有 cost 均为 None，F4 分支按字面条件不可触发；"连续多轮输出完全相同的不可行解"（violations 逐字相同）在现有管线中会被 F2 吸收。F4 分支的保留意义：分类法完整性（六类之一）+ 对未来问题族的防御（若某问题对不可行解也报告 cost，如带罚函数的部分得分，F4 立即生效）+ W4 复核将实证检查 F4 缺席是否与"停滞被 F2 吸收"的解释一致。
- **预期频率**：**低**（结合可达性分析，当前问题族上预期为 0）。
- **对应文献现象**：HeuriGym 对进化框架失灵原因的第 ② 条——"跨迭代断上下文，反复修补同一个有缺陷的初始程序而无实质进展"（EoH / ReEvo QYI 0.4492 / 0.4486 均低于裸基线 0.6170）；DynaSchedBench 精化失效（Reflection 差于 CoT）。停滞是迭代式智能体的已知病理，值得一个专属编码位。

### 2.6 F5 预算耗尽（budget exhaustion）

- **定义**：max_iters 内未解出且预算先耗尽——三重预算闸门（调用次数 / token 总量 / 墙钟时间）之一在迭代上限之前关闸。
- **判定规则（自动）**：捕获 BudgetExhausted 异常 → status = "budget_exhausted"（solve_once 行 1388–1389）→ F5（行 1340–1341）。TDD 锚点 test_solve_once_budget_exhausted（行 1257–1264）。
- **判定依据（代码信号）**：Budget 在每次 solve_once 开头构造（行 1360），每轮循环先 `budget.check()`（行 1364）再调用、调用后 `record_call(prompt_tokens + completion_tokens)`（行 1370）；三闸判定见 budget.py 行 1141–1147（调用 ≥ max_calls → token ≥ max_tokens → 时间 ≥ max_seconds，按此顺序）。**闸门身份可事后推断**：异常消息含触发闸门（"调用次数达到上限 10"等），但 solve_once 捕获时未留存消息；由于 `budget.snapshot()` 的 calls / tokens / seconds 三列随行落盘（budget.py 行 1149–1151），触发闸门可由该三列与配置限值对照得出——按 check() 顺序取第一个达限者。**配置注记**：主 / 稳定性实验 max_iters=5 < max_calls=10，调用闸在这两组实验中休眠，F5 实际由 token 闸（60000）或时间闸（600s）触发——F5 是分析"预算约束是否成为大规模实例的实际瓶颈"的直接证据。
- **预期频率**：**低—中**，集中在 large 档。先验：《计划》风险表将"大规模实例 LLM 几乎全失败"列为高概率已知现象；大规模长输出（TSP n=200，temperature 0.7）在 5 轮内累计触顶 600s 时间闸的可能性最高。
- **对应文献现象**：无直接对应——四大基准均无预算闸门（D2：HeuriGym 超时计入六类异常的 TimeoutError 是最接近的先例，但其超时是问题专属资源约束而非项目级三重预算）。F5 是本分类法中唯一由 EvalBench 自身的成本受控机制（D2 对策）产生的新失败类，也是降级①后预算维度仍留在失败分析中的唯一通道。

### 2.7 F6 其他（unclassified / manual）

- **定义**：以上皆不匹配的失败，人工复核归类（《计划》Task 2.3：F6 归入 F1–F5 哪类由人判断）。
- **判定规则（人工为主）**：代码通道有二——空 transcript（行 1342–1343，防御分支，常规配置不可达，见 §2.10）与八分支兜底（行 1355）。复核阶段人工可将任何自动标注改判（含维持 F6）。
- **判定依据（代码信号）**：无——这正是 F6 的定义特征：无确定性信号可判，才需要人。
- **预期频率**：**低**。预期主要由复核改判贡献而非自动标注贡献。
- **对应文献现象**：HeuriGym 六类异常中的 API Error 一类同为"环境噪声兜底"性质。

### 2.9 判定优先级的设计理由

优先级 F5 > F1 > F3 > F4 > F2 > F6 的每一级排序都有明确理由：

1. **F5 最先——环境信号最确定**。BudgetExhausted 是三重控制器抛出的环境级异常（budget.py 行 1141–1147），判定不依赖对模型输出的任何解释，是六信号中唯一来自"运行环境"而非"解内容"的信号；且它直接解释了 run 为何终止（预算门先于迭代上限关闸）。若不优先，预算耗尽的 run 会按末轮输出被误标为 F1 / F2 / F3——把"环境截断"误归因为"模型失败"，既冤枉模型也污染失败统计。
2. **F1 次之——解析先于验证**。parse() 在 evaluate() 上游：解析失败时解对象根本不存在，violations 只是占位 `["解析失败"]`（行 1372–1373），此时谈论幻觉或约束违背没有对象。F1 必须在一切"解层面"判定之前。
3. **F3 先于 F2——更根本**。F3（越界 / 不存在）意味着模型对解空间本身的表示出错——引用了 n 个城市 / 物品、m 台机器之外的对象，是"世界模型"级错误；F2（数量 / 重复 / 容量）意味着模型理解解空间但在组合推理或容量核算上失败，是"搜索 / 推理"级错误。两者对症改进方向不同（F3 → 提示词与格式约束；F2 → 反馈质量与推理能力），主类别取更根本者。验证器内部检查顺序亦同构佐证：TSP 先查越界（行 581–583）再查完整性（行 584–586），BPP 先记越界（行 737–738）再记缺失 / 重复（行 739–743）；调度问题例外——长度检查（行 805–807）先于越界（行 811–813），但 label_failure 层面的 F3 > F2 只看 violations 文本关键词、与验证器内部顺序无关，优先级不受该例外影响。
4. **F4 先于 F2——过程蕴含终态**。末两轮 cost 相同说明迭代已停止产生新候选，终轮不可行只是停滞的必然结果；标 F4（过程性失败）的信息量大于标 F2（终态失败）。
5. **F6 最后——兜底**。以上皆不匹配才归 F6，交人工复核；它是分类法的"未知未知"容器，而非具体失败机制。

### 2.10 可达性注记（如实记录）

对《计划》代码的三个如实观察（非新增机制，均为防御性设计的边界说明）：

1. **F4 分支在当前问题族上不可触发**（§2.5 已述）：不可行 ⇒ cost=None，可行 ⇒ 立即 solved，故失败 run 的 costs 全为 None，`costs[-1] is not None` 恒假。TDD 亦如实反映——test_runner.py 覆盖 F1 / F3 / F2 / solved 四分支与 F5（行 1257–1284），F4 无专门测试。
2. **末分支 F6（行 1355）同样不可达**：末轮 parsed=True 且 violations 为空 ⇒ 该轮可行 ⇒ 已 solved 矛盾；三问题验证器不可行分支必带非空 violations。
3. **空 transcript F6（行 1342–1343）为防御分支**：常规配置（max_iters ≥ 1）下循环至少执行一轮；仅退化配置（如 max_iters=0）或异常路径触达，且它是后续 `transcript[-1]` 访问的必要守卫。

三条注记的共同含义：**自动标注的实际产出类为 F1 / F2 / F3 / F5（+F6 复核通道）**；F4 与两个 F6 通道以"完整分类法定义 + 防御性代码"的形式存在。W4 Task 4.4 的 10% 抽检将实证核对此预期。

## 4. 半自动标注流程

**分工原则**：判定规则全部锚定在确定性代码信号上（parsed 布尔、violations 字符串、cost 序列、BudgetExhausted 异常），机器可复判、可重放——因此 F1–F5 全部由 runner 在运行时自动标注，落 `row["failure_class"] = label_failure(status, transcript)`（行 1398）；人工只做机器做不了的两件事：F6 的归类判断、自动规则的抽检校准。

**流程（W4 Task 4.4，三步）**：

1. **导出失败清单**：用 pandas 过滤 `failure_class != ""`，输出 run 目录、transcript 路径、自动类别——即全部失败 run 的复核工作台。
2. **逐条复核**：打开 transcript 复核。重点一：F6 run 归入 F1–F5 哪类（或维持 F6）；重点二：**自动标注抽检 10%**（对 F1–F5 的自动标注按比例抽样，人工判读 raw 与 violations 是否支持该归类）。修正结果记入 `results/<run_id>/failure_review.csv`，五列：**instance, repeat, auto_class, manual_class, note**。
3. **回填真实示例**（§3 的闭环）。

**产出与度量**：failure_review.csv 是自动分类法的校准数据——抽检样本上 auto_class 与 manual_class 的一致率将写入报告（一致率高 ⇒ 判定规则有效；分歧集中于某类 ⇒ 该类的文本关键词或判定顺序需要修订，修订属设计迭代、须记入报告 Discussion）。图 5（report.py fig5_failure_modes.png，行 1617–1627）按模型 × 失败类堆叠呈现最终分布；本报告的失败统计一律以 manual_class 修正后的口径为准，auto_class 原值保留在 summary.csv 供审计。

## 5. 失败-规模交叉统计

### 5.1 F5 的预算信号

## 6. 展望：FuzzGPT 式失败种子再利用

分类法的终局价值不止于统计，还在于失败样本的系统再利用。FuzzGPT（ICSE'24，ref5 笔记）证明了闭环在测试领域已跑通：历史 bug 触发程序做种子，使 LLM 生成的覆盖率比 TitanFuzz 高 36.03% / 60.70%，CoT"先写失败成因再生成"进一步提升（23,945 vs 22,922），且低预算下高效（FS-25 以 25 程序/API 超过 TitanFuzz 全量）。ref5 笔记已给出到 EvalBench 的六步迁移逻辑链，本节将其落到本文的分类法上：

1. **失败矿工**：transcripts 天然记录逐实例行为，抽取 (失败实例, 失败模式标签) 对——标签即本文 F1–F6。对照 FuzzGPT 的 buggy API 标注需 self-training（精度仅 76%），我们的标签由评测 harness 确定性产生，标注环节零成本、零误差。
2. **CoT 失败成因先验**：让生成模型先描述失败成因（如"该实例因解空间对称性高，导致 agent 幻觉下标"）再生成实例——FuzzGPT Table 3/6 证明 CoT 中间步一致提升覆盖率。
3. **三种注入方式**：few-shot（K=3–6，K 过大反降；示例随机选即可，MMR 消融不优于随机）为首选；zero-shot completion（失败实例前缀补全）次之；fine-tuning 仅设计层面保留（每任务单独训练成本已被 FuzzGPT 自认，课程项目排除）。
4. **三道验证闸**：有效性过滤（实例良构且参考求解器可解）→ 差分 oracle（被测 agent 输出 vs OR-Tools 参考解）→ 难度确认（复跑确认目标 agent 确实失败，防"伪困难"）。
5. **成本台账**：FS-25 证明失败种子化生成在极低预算下高效——每失败类只需 10–25 个种子，采样参数与生成数入台账，与本项目"成本受控"主旨同构。
6. **自适应难度闭环**：eval → transcripts 沉淀失败 → 失败种子生成困难实例 → 过滤确认 → 回灌测试集——"history-driven benchmark hardening"。

**边界（ref5 笔记已论证，此处仅援引）**：失败归因前提——只把结构诱发型失败（退化约束、近不可行、数值不稳）当种子，能力性失败的种子只会复制同难度实例；平凡失败污染——F1 格式性失败做种子价值低，应优先 F2 / F3 的推理型失败；同源偏差——生成器与被测对象跨 LLM 家族，防"该族恰好失败"的确认循环。**课程定位**：ref5 笔记明言"只论证到设计层面 incorporation"——本节即该设计层论证；实施只需在分析层加一个生成模块（评测内核不动），transcripts 全量落盘（评测协议文档 §4）已保留全部原料。
