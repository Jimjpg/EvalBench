## 1. 实验矩阵

### 1.0 总览

| 维度 | 主实验 `exp_main.yaml` | 稳定性 `exp_stability.yaml` |
|---|---|---|
| 模型 | deepseek-chat、qwen-plus（各 temperature 0.7） | 同左 |
| 问题 | tsp / binpacking / pmachine | 同左 |
| 规模 | small / medium / large 三档 | 同左 |

| 回答的问题 | 质量 / 可行性 / 成本 / 失败的 (模型 × 问题 × 规模) 地图（H1、H4） | 同配置重复下的采样方差（D5、图 4；亦为 H1 / H2 提供噪声基准） |

规模档取值（`Problem.sizes`，随仓库版本化）：TSP n = 10 / 50 / 200（行 564）；BPP 物品 20 / 60 / 120、容量 100（行 717–718）；P||Cmax 作业 20 / 60 / 120 × 机器 4 / 8 / 12（行 792–793）。

### 1.1 主实验 `exp_main.yaml`（90 runs）

配置全文（《计划》Task 4.1 Step 1 原文，行 1713–1736）：

```yaml
run_name: main
models:
  - name: deepseek-chat
    base_url: https://api.deepseek.com
    env_key: LLM_API_KEY
    temperature: 0.7
  - name: qwen-plus
    base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
    env_key: DASHSCOPE_API_KEY
    temperature: 0.7
problems:
  - name: tsp
    scales: [small, medium, large]
  - name: binpacking
    scales: [small, medium, large]
  - name: pmachine
    scales: [small, medium, large]
instances_per_scale: 5
repeats: 1
max_iters: 5
budget:
  max_calls: 10
  max_tokens: 60000
  max_seconds: 600
```

设计要点：每 (模型, 问题, 规模) 组合 5 个实例，来自 seed 1–5 的确定性生成（`problem.generate(n, seed)`）——实例本身可由配置 + 代码复现；single repeat 使主实验测"平均能力"，方差交给稳定性实验；standard 预算对全部 90 runs 统一，保证 (模型 × 问题 × 规模) 三个维度上的比较在等预算下进行（等预算公平比较是 D2 对策的核心，预算不随问题难度浮动）。

### 1.2 稳定性实验 `exp_stability.yaml`（90 runs）

配置 = exp_main 但 `instances_per_scale: 3`、`repeats: 5`、每问题三个规模（《计划》Task 4.2 Step 1，行 1752）——即 2 模型 × 3 问题 × 3 规模 × 3 实例 × 5 重复 = 90 runs，温度 0.7 与主实验相同。

设计要点：其一，**稳定性来自受控重复而非温度对比**——temperature 固定 0.7（与主实验一致），度量的是"同配置重跑"的采样方差，对照 HeuriGym 温度固定 0 且单次运行无重复方差报告、FrontierCO 单次运行以跨实例标准差冒充重复（D5 批评的缺口）；温度 0→1 的对比是 HeuriGym 的消融设计，不在本矩阵内。其二，**实例取 seed 1–3（主实验的子集）**：参考解经 references.json 缓存共享、无需重算，且主实验的 single-repeat 结果可与稳定性实验的前 3 实例对照，抽查 run 间一致性。其三，产出 stability_cv = 同 (模型, 问题, 实例) 5 次重复 primal_gap 的 pstdev/mean（metrics.py 行 416–422），报告以"均值 ± CV"呈现（图 4）。

### 1.3 【已裁剪】预算档位实验（降级预案①）

**裁剪决策**：2026-10-06 启用《计划》§0 降级预案①（行 26 / 28）——预算档位实验（Task 4.3）、图 6 预算-性能曲线、假设 H3 一并裁剪，实验矩阵由三组收缩为两组（234 → 180 runs）。**理由**：课程时间约束（单人六周，W4 单周需完成实验 + 失败复核 + 汇总，三组串行预算档位实验挤占稳定性实验与复核质量）；降级序位①是计划预定的第一刀，W1 / W2 交付物不受影响。

**原设计（留档）**：2 模型 × TSP × 3 规模 × 3 实例 × 1 重复 × 3 档预算 = 54 runs；三档配置仅 problems 限定 tsp、`instances_per_scale: 3`、`repeats: 1`，budget 分别为 tight `{max_calls: 3, max_tokens: 15000, max_seconds: 120}` / standard `{10, 60000, 600}` / loose `{20, 150000, 1800}`（《计划》Task 4.3 Step 1，行 1760–1763）；产出图 6"预算-性能曲线"（x = 三档预算分类轴，y = 各规模 QYI，三线 = small / medium / large，行 1765）与假设 H3"预算收紧对大规模实例伤害最大"。

**保留的预算机制**（裁剪"预算作为实验变量"，不裁"预算作为运行约束"）：① 三重控制器 Budget(max_calls, max_tokens, max_seconds) 随每次 solve_once 构造并逐轮 check；② standard 档三值（calls=10, tokens=60000, seconds=600）统一施加于全部 180 runs；③ F5 失败类（BudgetExhausted 捕获）仍使预算信号留在失败分析中（失败模式分类文档 §5.1——F5 占比即"预算是否构成实际瓶颈"的判据）；④ api_cost 折算与成本-质量前沿（图 1）不受影响。

**恢复路径（后续工作）**：配置文件模板已在《计划》中保留——第 1 节文件结构含 `configs/exp_budget_{tight,standard,loose}.yaml`（行 86），Task 4.3 三步原文未删除、仅标记"跳过本任务"（行 1755–1765）。恢复 = 按 Task 4.3 Step 1 建 three 配置 → 依次运行（三个独立 run 目录）→ 按 Step 3 手作图 6（10 行 pandas + matplotlib 脚本，合并三个 run 的 summary.csv 后 groupby）→ 假设 H3 从报告 future work 升级为正文检验。前置条件：课程周期外的时间窗口 + 约 ¥5 量级的增量预算（54 runs，§2 口径折算）。

## 2. 成本预算与熔断

**估算表**（《计划》Task 2.4 Step 2 口径：平均 2.5 次调用 / run、每调用约 2K in + 1K out；降级①后按 180 runs 重算）：

| 项 | 取值 / 算式 | 结果 |
|---|---|---|
| 平均调用数 | 2.5 次 / run（max_iters=5，多数 run 预计 2–3 轮内解出或失败） | — |
| 单调用 token | 2K in + 1K out | 3K |
| 原始总量 | 180 runs × 2.5 × 3K | ≈ 1.35M（0.9M in + 0.45M out） |
| 冗余系数 | ×2（大规模长提示 / 长输出、失败 run 打满 5 轮、重试） | **≈ 3M**（2M in + 1M out） |
| DeepSeek 单价全量折算 | ¥2/M in + ¥8/M out（运行当日到官网核对，report.py PRICE 表，行 1535–1538） | 2×2 + 1×8 ≈ ¥12 |
| 实际混合（deepseek 90 runs + qwen-plus 90 runs） | qwen-plus 单价 ¥0.8/M in + ¥2/M out（约为 DeepSeek 的 1/3–1/4） | ≈ ¥5–7 |
| **成本上界声明** | — | **< ¥20** |

口径说明：《计划》Task 2.4 Step 2 原估"总 token ≈ 4M、总成本 < ¥30"按裁剪前 234 runs（含 54 runs 预算档位实验）计；降级①后 180 runs 对应 ≈ 3M / < ¥20，两条口径一致（少 54 runs）。冒烟实验（exp_smoke.yaml，1 run）成本可忽略；参考解由 OR-Tools 本地计算并缓存（references.json），无 API 成本，一次性本地算力约 5–10 分钟（TSP medium + large 共 10 实例 × 30 s GLS 为主）。

**熔断线 ¥50**：超线立即中止运行排查（《计划》Task 2.4 Step 2"超 ¥50 立即中止排查"；风险表行 1827）。机制上的双保险：单 run 的 token 熔断（60000）封顶每次运行消耗，180 runs 的极端上界 ≈ 180 × 60K ≈ 10.8M tokens——即使全部 run 打满 token 闸且全部按较贵的 DeepSeek 单价、2:1 输入输出比折算，也仅 ≈ ¥43，仍在熔断线内。三重控制器由此在 run 级之外间接保护了项目级预算，熔断线是第二道而非唯一防线。

**分阶段充值建议**：先充 ¥10 覆盖冒烟 + 主实验（《计划》Task 3.9 Step 1"充值 ≥¥10"；风险表行 1822"DeepSeek 充 ¥10 足够"），跑完主实验用 report.py 核对实际 cost_yuan 与估算的偏差，再决定稳定性实验前的补款额度——估算—实测对账本身是成本受控主张（D2）的执行证据。备用：Qwen 免费额度（DASHSCOPE_API_KEY）；保底 Ollama 本地 qwen2.5:7b（改 base_url 即可，报告注明）。

## 3. 可检验假设

报告结果章按 H1 / H2 / H4 组织（《计划》Task 4.5 Step 1：每条假设写结论 / 关键数字 / 图表引用三行）。**原 H3"预算收紧对大规模实例伤害最大"已随降级①裁剪**（《计划》Task 2.4 Step 3 括注，行 234），报告中作为 future work 表述（恢复路径见 §1.3）。

### H1 可行率随规模增大显著下降

- **陈述**：对每个 (模型, 问题) 组合，small → medium → large 的组级可行率单调下降，且降幅超出重复采样波动。
- **文献先验**：HeuriGym 演示集（5 实例）与评估集（数十个大规模实例）规模相差 ≥1 个数量级，SOLVE^III 在大规模问题上坍塌（全局布线 9 模型全 0，总体最好 GPT-o4-mini-high 亦仅 74.8%）；FrontierCO 规模效应（LEHD 合成基准 0.72% gap → easy TSP 10% → hard TSP 77%；MDS-hard 神经方法 gap 全 100%）；《计划》风险表将"大规模实例 LLM 几乎全失败"列为高概率已知现象。
- **判伪标准**：任一 (模型, 问题) 组合中三规模可行率未呈单调下降，或相邻规模降幅在稳定性实验测得的重复波动（stability_cv × 均值）范围内——即降幅可被采样噪声解释——则 H1 对该组合不成立；全部 6 个组合均不成立则 H1 整体证伪。
- **对应图表**：图 3（可行率随规模衰减，按模型）；图 2（primal_gap vs 规模）为伴随视图——不可行解 gap=1 会同步推高均值，两图应同向。
- **数据**：summary.csv `feasible` 列按 (model, problem, scale) 分组均值。

### H2 迭代反馈提升可行率但边际收益递减

- **陈述**：验证反馈驱动的迭代循环（生成 → 解析 → 验证 → 反馈修正，至多 5 轮）提升累计可行率，但增益随轮次递减，主要收益集中在前 2–3 轮。
- **文献先验**：HeuriGym SOLVE@i 分布——GPT-o4-mini-high SOLVE^III @1=53.2% → @5=69.7% → @10=74.8%（前 5 轮 +16.5 个百分点、后 5 轮仅 +5.1）；Claude-3.7-Sonnet @1 仅 9.2%，高度依赖迭代修复。反向先验同样存在：Gemini-2.5-Pro 1 / 5 / 10 轮 0.6253 / 0.6259 / 0.6170（过量反馈反噬）、DynaSchedBench 精化失效（Reflection 1.7% 差于 CoT 0.7%）——H2 的"递减"半句因此有真实的证伪风险，非安全假设。
- **判伪标准**：累计可行率在第 3 轮之后的增量（iter 4–5 两轮合计）仍 ≥ 10 个百分点，则"边际收益递减"被证伪；若累计可行率随轮次不升反降，则前半句"提升"亦被证伪。
- **对应图表**：transcript iter 统计——由 summary.csv `status` 列（solved_iter1…solved_iter5）构造累计可行率曲线 @k = P(solved_iter ≤ k)；本实验 max_iters=5，观测窗口为 @1–@5（对照 HeuriGym 的 @1/@5/@10 刻度）；transcripts 逐轮 `feasible` 字段可供核对中间轮次。
- **数据**：`status` 列（solved 路径）+ transcripts（逐轮 feasible / violations）。

### H4 两模型 QYI 接近但性价比（QYI/¥）差异显著

- **陈述**：deepseek-chat 与 qwen-plus 的模型级（加权）QYI 相近，但单位成本的质量（QYI/¥）因单价差（¥2/¥8 vs ¥0.8/¥2，输入 / 输出每百万 token）显著分化——qwen-plus 预期占据成本-质量前沿的左上高性价比区。
- **文献先验**：HeuriGym 图 2 右图成本-质量前沿——顶级模型 QYI ≈ 0.6 但估计成本差 3–4 倍，Gemini-2.5-Flash（单价 0.15/3.5 $/M）以 QYI 0.5682 被判"性价比最优"；同代中端模型质量接近而单价分化（DeepSeek-V3 QYI 0.3707 vs Qwen3-235B 0.4355，输出单价 1.10 vs 2.86 $/M）。
- **判伪标准（本文操作化口径，供 Task 4.5 核对）**：两模型加权 QYI 之差 ≥ 0.1（"接近"不成立），或 QYI/¥ 之比 < 2（单价优势未转化为 ≥ 2 倍性价比，"差异显著"不成立）。
- **对应图表**：图 1（成本-质量前沿：x = cost_yuan 总和，y = 加权 QYI，每模型一点——HeuriGym 图 2 右图的直接复刻）；表 1 的 yuan / gap / feasible 列。
- **数据**：`quality` / `feasible` 列（QYI）+ `tokens_in` / `tokens_out` 列 × PRICE 表（cost_yuan）。

## 4. 基线对照表设计

### 4.1 三层对照结构

| 层 | TSP | BPP | P\|\|Cmax | 性质 |
|---|---|---|---|---|
| LLM（被测） | deepseek-chat / qwen-plus | 同左 | 同左 | 5 轮迭代 + standard 预算，temperature 0.7 |
| 经典基线 | 最近邻 + 2-opt（baselines.py 行 893 / 904） | FFD（行 951） | LPT（行 989） | 确定性、单次、零 API 成本 |
| 参考解（OR-Tools，30 s 口径） | n ≤ 10 全排列精确；n > 10 路由求解器 GLS 30 s（行 920–946） | ≤ 25 项 CP-SAT 精确；> 25 项 FFD（行 963–984） | ≤ 25 作业 CP-SAT 精确；> 25 作业 LPT（行 996–1016） | primal_gap / quality 的 `reference` 来源 |

三条口径注记（与指标体系文档 §5 对齐）：其一，**规模档与求解口径恰好对齐**——三问题 small 档全部落精确分支、medium / large 落启发式分支；因此 BPP 与 P||Cmax 的 medium / large 参考解**就是** FFD / LPT（经典基线与参考解合一，对照表中两列相同是设计使然而非冗余），而 TSP 的 NN+2-opt 独立于 GLS 参考解，可单独度量"贪心启发式与 30 s 限时搜索的差距"。其二，**回退路径**：OR-Tools 无解时 TSP 回退 NN+2-opt、CP-SAT 失败回退 FFD / LPT 上界，触发实例须在报告注明口径。其三，medium / large 参考解非严格最优，全部 gap / quality 读作"相对 OR-Tools 30 s 口径参考解"。

### 4.2 表设计（W4 交付物：≥ 4 张图 + 1 张基线对照表）

行 = (问题, 规模) × 方法（deepseek-chat / qwen-plus / 经典基线 / OR-Tools 参考解），共 3 问题 × 3 规模 × 4 方法 = 36 数据行；列 = 目标值（cost 均值）、primal_gap 均值、可行率、tokens 与 api_cost（仅 LLM 两行有值）、口径注记（精确 / 启发式 / 回退）。LLM 行来自 summary.csv；基线与参考解行由 baselines.py 确定性重算（零 API 成本，参考解亦可直接读 references.json 缓存）。表以 pandas 脚本于 W4 汇总阶段拼装（与《计划》Task 4.3 Step 3 手作脚本同款做法），落 `report/figs/`，满足 §0 里程碑 W4 验证标准"≥ 4 张图 + 1 张基线对照表"（行 23）。

### 4.3 为什么不做人类专家基线

CO-Bench 的对照协议是"每题约 30 min 人机对齐研究预算 + 开发期 64 research steps"的人类专家求解，并据此定义 Above Human（AI 在 25/36 = 0.6944 的问题上超过专家基线）与 Valid Solution（最好 agent 0.5555 仍低于人类专家 0.6111）两个指标。该协议需要领域专家逐题投入 30 分钟量级时间，超出单人六周课程项目的资源边界。本设计以 OR-Tools 30 s 口径参考解为对照锚——可复现（代码 + 时间限全公开）、零边际成本、口径可审计；CO-Bench 的人类对照做法在报告 Related Work 中作为对照引用，人类基线列为后续工作。

## 5. 执行与断点续跑

**resume 机制**（runner.py 行 1457–1462、1473–1475）：Runner.run() 启动时若 run 目录已有 summary.csv，则重建 `done = {(model, problem, scale, instance, repeat), …}` 五元组集合；循环内命中即 continue——同配置重启自动跳过已完成行，中断恢复零额外记账（《计划》Task 4.1 Step 2"可中断重跑，resume 自动跳过已完成行"）。注意 resume 的粒度是整行（一次完整智能体循环），run 中断在半轮的实例会整轮重跑，幂等安全。

**执行顺序**（与《计划》任务序一致）：

1. **冒烟**（Task 3.9，exp_smoke.yaml：1 模型 × tsp small × 1 实例 × 1 重复，max_iters 2）——端到端验证 config / manifest / summary / transcripts / 图表五件套，成本可忽略；
2. **主实验**（Task 4.1，约 1–2 小时，可中断重跑）——先产出 (模型 × 问题 × 规模) 全量地图；

**(a) 大规模全失败——作为 H1 发现呈现，不作为实验事故**：large 档可行率坍塌本身就是 H1 的实验发现，按数据如实呈现；分析区间以 medium 为主。对照 FrontierCO 的教训——hard 集上大量 gap=1 记录"更多反映能否产出可行解而非解质量梯度"——报告 Discussion 须说明 large 档的区分度局限，不以 large 档的 gap 均值做模型质量排名。

**(b) 解析率过低——prompt v1 → v2 升级路径**：v1 已含格式示例与"只输出 JSON"指令，解析器已容错 markdown 围栏；仍低则在 prompt() 中加 one-shot 完整示例，`PROMPT_VERSION` 改 "v2" 并写入 manifest.json 的 prompt_version 字段（行 1333、1429）——v1 / v2 的 run 以 manifest 区分，不混跑；若升级发生在主实验中途，已完成的 v1 行不删除、以 manifest 分层报告（配置 + 日志全留存的审计原则优先于数据整齐）。升级决策的触发线与 F1 占比的联动见失败模式分类文档 §2.2 / §4。

**(c) API 成本熔断**：超 ¥50 立即中止运行；排查重点为大规模实例是否批量耗尽 max_iters（token / 时间闸连续触发，F5 占比异常升高即信号，见失败模式分类文档 §5.1）；收紧 budget 后续跑。§2 已说明三重控制器的 run 级 token 熔断使熔断线在机制上有双保险，正常路径下不应触达。
